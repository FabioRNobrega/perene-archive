## Problem Statement

`ArchiveService.Move`/`Rename`/`MoveToTrash` (`WebApp/WebApp/Services/ArchiveService.cs:180-244`) and `ArchiveService.EmptyTrash` (`WebApp/WebApp/Services/ArchiveService.cs:224-249`) all run synchronously inline inside the HTTP request that `ArchiveEndpoints.Move`/`MoveToTrash`/`EmptyTrash` (`WebApp/WebApp/Endpoints/ArchiveEndpoints.cs:53-55, 331-385`) handle, and `ArchiveBrowser.razor`'s `MoveAsync`/`DeleteAsync`/`EmptyTrashAsync` (`WebApp/WebApp.Client/Components/ArchiveBrowser.razor:1635-1653`) call them through `SendMutationAsync`, which sets `_operationPending = true` and simply awaits the whole `HttpClient` call with no intermediate feedback. `EmptyTrash` walks the trash root's top-level entries and calls `Directory.Delete(path, recursive: true)`/`File.Delete(path)` one entry at a time — for a large recursive folder or a trash root containing many files, the .NET runtime deletes each nested file/subdirectory individually, so this loop can run for a long time with the request (and the Blazor UI, which shows no progress at all beyond a generic pending state) apparently frozen. `Move`/`MoveToTrash`'s `MovePhysical` (`WebApp/WebApp/Services/ArchiveService.cs:944-951`) calls `Directory.Move`/`File.Move` directly; these are effectively-instant metadata renames only when source and destination sit on the exact same underlying filesystem, but the archive root the user points `ArchiveRootOptions.Path` at is frequently a NAS-backed bind mount, and large folders/files can still take a long time to move — with, again, no feedback while the request is in flight. The user needs to see real progress (not just a spinner) while a large move or permanent delete is running, instead of the page appearing to freeze.

## User Stories

- Given the user moves a large folder (or a folder containing many files) to another category/folder, when the move is running, then the UI shows a progress popup with supporting text and a progress bar instead of an indefinite blocking state.
- Given the user sends a large item to Trash (soft-delete via `MoveToTrash`), when that move is running, then the same kind of progress popup appears.
- Given the user empties Trash while it contains a large recursive folder or many files, when the delete is running, then the UI shows a progress popup tracking how many of the trash root's files have been removed so far.
- Given a move or delete finishes successfully, when the background job completes, then the popup shows a completed state, the archive listing refreshes to reflect the change, and the popup can be dismissed (or auto-dismisses).
- Given a move or delete fails partway through (e.g. a conflicting name appears, an `IOException`/`UnauthorizedAccessException` occurs, or the destination becomes invalid), when the job stops, then the popup shows a failed state with a diagnostic message, and the archive listing still reflects whatever partial state resulted (no crash, no silently-lost error).
- Given the user navigates within the Archive Browser or reloads while a move/delete job is still running, when the job status is polled, then the popup can reappear/keep reflecting the true server-side job state, because the job's progress lives server-side, not only in local component state.

## Functional Requirements

1. FR1 — `ArchiveService.Move`, `ArchiveService.MoveToTrash`, and `ArchiveService.EmptyTrash` no longer run synchronously inside the HTTP request. Their filesystem work moves into a new background job pipeline (queue + background worker), following the existing `ICompositionJobQueue`/`CompositionBackgroundWorker`/`ICompositionJobStatusStore` pattern (`WebApp/WebApp/Services/ICompositionJobQueue.cs`, `CompositionJobQueue.cs`, `ICompositionJobStatusStore.cs`, `CompositionJobStatusStore.cs`, `CompositionBackgroundWorker.cs`).
2. FR2 — `PATCH /api/archive/{category}/items/{id}/location` (Move), `DELETE /api/archive/{category}/items/{id}` (MoveToTrash), and `DELETE /api/archive/{category}/items` (EmptyTrash) validate the request synchronously exactly as today (category/item/folder resolution, name-conflict and self-move checks) but, instead of performing the filesystem operation inline, enqueue a job and return immediately with a job id and its initial `Pending` status (HTTP 202-style payload) rather than the final `ArchiveListingDto`.
3. FR3 — `ArchiveService.Rename` is unchanged: renames are single-entry, same-directory operations with no large-scale recursive I/O, so they keep running synchronously as today. Only `Move`, `MoveToTrash`, and `EmptyTrash` move to the background job pipeline.
4. FR4 — A new background worker drains one archive-mutation job at a time (matching the existing one-job-at-a-time worker pattern used by `ThumbnailBackgroundWorker`/`CutBackgroundWorker`/`CompositionBackgroundWorker`) and executes the actual `Directory.Move`/`File.Move`/`Directory.Delete`/`File.Delete` work previously done inline, reporting progress as it goes.
5. FR5 — Before starting the filesystem work, the worker computes a total item count for the job: for `EmptyTrash`, the total number of files under the trash root (recursive, using the same `Directory.EnumerateFiles(..., EnumerationOptions { RecurseSubdirectories = true })` pattern already used by `ArchiveMetricsService.CountFiles()`); for `Move`/`MoveToTrash` of a folder, the total number of files under that folder; for a single file, the total is `1`. This total is stored on the job status alongside a live processed-count that increases as the operation proceeds.
6. FR6 — For `EmptyTrash`, the worker deletes file-by-file/subdirectory-by-subdirectory (rather than a single opaque `Directory.Delete(recursive: true)` call) so it can increment the processed-count after each file removal and expose real incremental progress; folder structure itself is removed once its contents are empty.
7. FR7 — For `Move`/`MoveToTrash` of a single file, the worker performs the existing `File.Move` call and reports `0/1` then `1/1` (no meaningful intermediate progress is possible or required for a single file). For `Move`/`MoveToTrash` of a folder, the worker walks the folder's files, moving each one to the mirrored destination path and creating destination subdirectories as needed, incrementing processed-count per file, then removes the now-empty source subtree; this replaces the single `Directory.Move` call so progress can be observed. If the destination filesystem is the same as the source, this still behaves correctly (just as fast as before) — it's the large-folder/cross-filesystem case that gains visible progress.
8. FR8 — A new in-memory job status store (mirroring `CompositionJobStatus`/`ICompositionJobStatusStore`) tracks `JobId`, `Kind` (`Move`/`MoveToTrash`/`EmptyTrash`), `State` (`Pending`/`Processing`/`Completed`/`Failed`), `TotalItems`, `ProcessedItems`, a human-readable label (e.g. the item's display name, or "Trash" for EmptyTrash), and an optional failure `Diagnostic`.
9. FR9 — A new `GET /api/archive/jobs/{jobId}` endpoint (or `GET /api/archive/jobs` returning all jobs from the current application session, matching `GET /api/dashboard/jobs`'s shape) returns the current status of one or more archive-mutation jobs so the client can poll it.
10. FR10 — `ArchiveBrowser.razor`'s move/delete/empty-trash triggers (`StartMove`/`MoveAsync`, `DeleteAsync`, `StartEmptyTrash`/`EmptyTrashAsync`) enqueue the job via the updated endpoints, then show a Bootstrap modal/popup containing the item's display name, a status line ("Moving…", "Deleting…", "X of Y items"), and a `progress`/`progress-bar` element following the same striped/animated markup convention as `DashboardConversionJobsTab.razor`; while the job is `Pending`/`Processing`, the component polls `GET /api/archive/jobs/{jobId}` on a `PeriodicTimer` (2s, matching `DashboardConversionJobsTab.PollAsync`) and stops polling once the job reaches a terminal state.
11. FR11 — When the polled job reaches `Completed`, the popup shows a success state and the component re-fetches the current archive listing (`GET /api/archive/{category}/items?...`) exactly as `SendMutationAsync` does today, then the popup is dismissible (close button) or auto-dismisses after a short delay.
12. FR12 — When the polled job reaches `Failed`, the popup shows the failure `Diagnostic` (e.g. "An item with that name already exists in the destination folder.", or a generic I/O failure message) with a close button; the archive listing is still re-fetched so the UI reflects whatever partial state exists server-side.
13. FR13 — If a `Move`/`MoveToTrash` job fails partway through (e.g. an unexpected `IOException` on one file), files already moved before the failure remain moved (no automatic rollback); the failure diagnostic communicates this by naming the operation as partially completed, and the resulting listing reflects the true on-disk state. This mirrors the existing "no rollback" behavior implicit in today's single-call `Directory.Move`.
14. FR14 — The job queue processes archive-mutation jobs one at a time (matching the existing background-worker convention); while a job is in flight, the endpoints in FR2 still accept new mutation requests for other items and enqueue them (bounded queue, matching `CompositionJobQueue`'s `Channel`-backed bounded-queue-with-wait pattern), rather than rejecting concurrent requests outright.
15. FR15 — All job endpoints only ever expose the job id, kind, display label, state, and item counts — no physical or root-relative filesystem path is ever included in a job's client-facing payload, consistent with the existing archive opaque-ID boundary.

## Non-Functional Requirements

- No physical or root-relative filesystem path is ever exposed to the browser or written to normal application logs, consistent with the existing archive opaque-ID boundary.
- The new queue/status-store/worker/generator responsibilities are split into small, focused services (an `IArchiveMutationJobQueue`, `IArchiveMutationJobStatusStore`, `ArchiveMutationBackgroundWorker`, and an `IArchiveMutationExecutor`/generator-equivalent that does the actual file I/O) rather than adding this logic directly to `ArchiveService` or `ArchiveEndpoints`, following the existing single-responsibility service pattern used by the Composition/Cut/Thumbnail pipelines.
- The new endpoints follow the existing minimal-API grouping convention in `MapArchiveEndpoints` (`WebApp/WebApp/Endpoints/ArchiveEndpoints.cs`) rather than being added ad hoc elsewhere.
- All new UI is built from Bootstrap components/utilities and Bootstrap Icons per `AGENTS.md`'s design-system constraints; no hand-authored SVGs or bespoke color CSS. The progress popup matches the existing modal and progress-bar conventions already used in this codebase (`ArchiveMovePicker`-style modal chrome, `DashboardConversionJobsTab.razor`-style progress bar).
- The background worker must not block other archive endpoints (listing, thumbnails, uploads) while a move/delete job runs, since it executes on its own `BackgroundService`, matching the existing Thumbnail/Cut/Composition worker isolation.
- Existing fast-path behavior (small files, single-file moves) must not become perceptibly slower because of the new job indirection; the enqueue-and-poll round trip should complete quickly enough that small operations still feel instantaneous to the user (short/no visible popup, or a popup that completes and auto-dismisses almost immediately).

## Out of Scope

- Adding pause/resume/stop controls for move/delete jobs (unlike the video-conversion job system) — these are enqueue-until-done operations only.
- Any change to `ArchiveService.Rename`, which stays synchronous.
- Byte-level progress reporting; progress is reported as a file/entry count (X of Y items), not bytes copied/deleted.
- Automatic rollback of partially-completed moves or deletes on failure.
- Persisting job history across an application restart — job status is in-memory only, matching the existing Composition/Cut job status stores.
- Any change to upload progress (`Specs/20260914112308-resumable-archive-uploads`, `Specs/20260915084301-upload-progress-preview-ui`) or video-conversion job progress (`Specs/20260916165205-video-conversion-compression-jobs`), which already have their own progress mechanisms.
- Concurrent/parallel execution of multiple move/delete jobs at once — one job runs at a time, exactly as the existing Composition/Cut/Thumbnail workers do.
