# Requirements: Durable Jobs and Naming Counters

## Problem Statement

Composition, archive-mutation, and conversion status stores are process-local, while output names are allocated by scanning directories. Restarts lose job state and concurrent workers can race. P4 makes status durable without exposing paths or stale browser snapshot IDs.

## Baseline from P1–P3 (as implemented)

- Every job record already carries `ActorUserId` (`CutJob`, `CompositionJob`, `VideoConversionJob`, `ArchiveMutationJob`), and workers already call `IFolderJobAuthorizer.CanRunAsync` before disk work (P2). A `null` actor currently means "internal, unchecked".
- Per-account job visibility is an in-memory, 2000-entry `JobOwnerRegistry`; Admins see all jobs.
- The three status-store interfaces are **synchronous** (`Seed`/`MarkProcessing`/`GetAll`…), and the stores are singletons; `AppDbContext` is scoped.
- Stable identity already exists: `MediaItem` (`long Id`, `FolderId`, `Size`, `LastWriteTimeUtc`, `ContentFingerprint`, `ContentRevision`, `Status`), resolved lazily by `MediaReconciliationService.EnsureAsync` (also used by `IUserMediaContext`). Folders have `long` ids via `FolderCatalog`; `/videos-cuts` and `/videos-composition` are seeded root folders.
- Latest migration is `RemoveLegacyImportRuns`; P4's migration follows it.
- Tests: `TestHostSecurity` signs in a fake admin that is **not** a database row, so any test that persists `JOB.UserId` (a foreign key) must use the real-Identity `AccountFactory`/`IdentityTestHost`.

## Functional Requirements

1. FR1 — Add a `JOB` table for Composition, ArchiveMutation, VideoConversion, and Cut jobs, with durable status, user (`UserId`, nullable FK, set null on account deletion), type, timestamps, and safe JSON payload. Cut has no status store or polling endpoint today; its row is written for durability/attribution only and adds no new endpoint.
2. FR2 — Payloads store stable `MediaItemId`/`FolderId` and captured identity values (size, mtime, `ContentFingerprint`, `ContentRevision`), never filesystem paths or snapshot IDs. Folder operations (folder move/trash, empty trash, move destination) use `FolderId`; file operations use `MediaItemId`. The in-memory queues keep carrying full job records for the running process; only the persisted payload is path-free.
3. FR3 — Reimplement the existing composition/archive-mutation/conversion status-store interfaces against SQLite so endpoint and UI shapes remain compatible, including conversion progress, pause/resume/stop state, and archive-mutation `processedItems`. Interfaces stay synchronous (singleton stores open a short-lived scope per call and use EF's synchronous API); progress writes are throttled so FFmpeg progress does not hit SQLite per tick. Terminal rows are retained up to a bounded count/age (replacing the registry's 2000-entry cap).
4. FR4 — `JOB.UserId` replaces `JobOwnerRegistry`: members list only their own jobs, Admins see all, and ownership survives restart. A job whose account was deleted keeps its row with `UserId = null` and is visible to Admins only.
5. FR5 — On startup (web host only, inside `StartupInitializer` after migrations; never from `AdminCli`), mark every non-terminal persisted job as `Failed` with a generic "interrupted by restart" reason. Persisted jobs are never replayed.
6. FR6 — Resolve snapshot IDs to stable identity at enqueue (`JobEnqueueService`, the only browser-ID → identity boundary, reusing `MediaReconciliationService.EnsureAsync`). At execution, `JobExecutionRecheckService` verifies Active state and captured identity, then **delegates** authorization to the existing `IFolderJobAuthorizer`; it does not reimplement the folder checks. Failures are generic. A durable job whose `UserId` is null because the account was deleted must **fail**, not be treated as an internal/unchecked job: "internal" is an explicit job origin, not a missing user.
7. FR7 — Replace cut, composition, image-crop, and video-conversion directory scans with a `NamingCounters` atomic allocator. The counter key is `(kind, output folder, prefix, extension)` (image crop and conversion write beside the source, so the output folder varies; cut and composition use their fixed roots). A counter is seeded from the existing files on first use and then only increases.
8. FR8 — Preserve output naming formats (`<prefix> NNNN.<ext>`, `<prefix> Composition NNNN.mp4`) and ensure concurrent allocations are unique, consecutive, and never regress after deletion. Allocation is a short transaction; a failed job may leave a gap (no rollback of the counter), which is acceptable but must not cause reuse.
9. FR9 — The Jobs tab shows who started each conversion job ("Started by <display name>", or "Removed account" when the owner was deleted). The display name is read from the owner's account when jobs are listed; no user ID is sent to the browser. Members only ever see their own jobs, so for them it shows themselves.
10. FR10 — A Failed or Stopped conversion job (including one interrupted by a restart) offers **Retry**. The conversion payload therefore also stores the user's original selection (mode, output height, quality preset, target size, subtitle track, burn-in; no paths) and the archive category key. Retry (`POST /api/dashboard/jobs/{id}/retry`, owner or Admin, same antiforgery as the other job controls) resolves the source through its stable `MediaItemId` (must still be Active and on disk), re-probes it, re-resolves the profile from the stored selection, re-checks fresh Read/Create access for the caller, and **resets the same job** (same job ID, same row and card; status back to Pending, diagnostic and progress cleared, the retrier recorded as its owner) and queues it through the same path as a normal conversion. It is refused with a generic message when the job is not Failed/Stopped (409), predates stored selections, or its source is gone or changed, and while a conversion is already active for that file (409). Retry applies to conversion jobs only.
11. FR11 — The Jobs page lists **every** durable job type, not only conversions: conversions (unchanged rich cards with controls and Retry), compositions, archive moves/trash/empty-trash, and cuts. A type filter (All, Conversions, Compositions, Moves & trash, Cuts, each with a count) narrows the list. Visibility follows the same rule (members see their own jobs, Admins see all) and every card shows "Started by". Non-conversion cards are read-only: title, type, state badge, move progress, outcome text, and times. Every card, whatever its type, shows the same common details through one shared component: Started by, Queued, Started, Finished, Total time (from start, or from queue if it never started) and Result; type-specific rows (conversion profile and sizes, move progress) come after. To support Started/Total time for every type, `Job` records `StartedUtc` (set when it first runs, cleared by a retry). The Dashboard tabs (Overview, Jobs) carry Bootstrap Icons like the Family page tabs. The combined list is newest first. Cut rows therefore record a browser-safe label (source file name and A/B range, never a path) and a generic outcome, and are failed as interrupted on restart like the others. A new `GET /api/dashboard/jobs/activity` returns the non-conversion jobs; conversions keep `GET /api/dashboard/jobs`.
12. FR12 — The Jobs list is one fixed-height line per job instead of cards: type icon and label, status badge, name (truncated, full name in a tooltip), then a progress bar while active, the failure reason for Failed jobs, or Total time once finished, and icon actions (Pause/Resume, Stop, Retry where they apply) plus a details toggle. The toggle opens a panel with the shared details (FR11) and type-specific rows; open panels survive refreshes. Running jobs are pinned above finished ones, each group newest first. The list is paginated with Bootstrap pagination and a page-size selector (5, 10, 25 or 50 per page, default 10; changing the filter or the page size returns to page 1), and the list area scrolls while the title and type filter stay pinned. Row logic (labels, icons, ordering, filtering, paging, which actions apply) lives in a tested C# `JobListRules` class.

## Non-Functional Requirements

- Keep workers, FFmpeg authority, opaque IDs, and browser DTO contracts unchanged except for durable status behavior.
- Use short SQLite transactions and real-file concurrency tests; logs and payloads contain no physical or relative paths (counter keys live only in the database).

## Out of Scope

- Filesystem mutation journaling/recovery (P5).
- Resuming interrupted jobs; the Admin review queue; audio-track remux job persistence beyond reusing `IFolderJobAuthorizer.CanReadAsync` (it is cache-derived, not a `JOB` type).
