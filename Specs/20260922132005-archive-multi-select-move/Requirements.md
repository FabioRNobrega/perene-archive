## Problem Statement

`ArchiveBrowser.razor` (`WebApp/WebApp.Client/Components/ArchiveBrowser.razor`) currently lets a user move only one item at a time: each card's "Move" action (`StartMoveFromActions` → `StartMove` → `ArchiveMovePicker` → `MoveAsync`, `WebApp/WebApp.Client/Components/ArchiveBrowser.razor:1023,1649,1677`) opens the picker for a single `ArchiveItemDto`, which then calls `PATCH /api/archive/{category}/items/{id}/location` (`ArchiveEndpoints.Move`, `WebApp/WebApp/Endpoints/ArchiveEndpoints.cs:332-339`) for that one item. There is no way to select several files/folders in the current folder view and move them together, so relocating a batch of files means repeating "open actions → Move → pick destination → confirm" once per file. The `selected` concept that already exists on each card (`IsSelected`, `WebApp/WebApp.Client/Components/ArchiveBrowser.razor:1056`) means "currently playing/open in the player," not a multi-select for bulk actions, so it cannot be reused as-is. The user wants desktop-file-manager-style multi-select (as in KDE Dolphin): Ctrl+Click toggles an individual file in/out of the selection, and Shift+Click (optionally combined with Ctrl) extends the selection as a contiguous range from the last-clicked item to the newly clicked one, and the resulting selection can then be moved to another folder/category in one operation.

## User Stories

- Given the user is viewing a folder in the Archive Browser, when they Ctrl+Click an unselected card, then that card becomes selected (without opening the folder or playing the file), and Ctrl+Click on an already-selected card deselects it.
- Given the user has Ctrl+Clicked one card (the anchor), when they Shift+Click another card later in the same filtered listing, then every card between the anchor and the clicked card (inclusive) becomes selected, replacing any prior range selection but preserving the anchor.
- Given the user has 2+ cards selected, when they look at the Archive Browser, then a selection toolbar/bar appears showing the count of selected items and a "Move" action and a "Clear selection" action, without requiring them to open each item's individual actions panel.
- Given the user chooses "Move" with multiple items selected, when they pick a destination category/folder in the existing move picker and confirm, then all selected items are moved there as a single background job, and the existing move-progress popup (`Specs/20260922122650-archive-move-delete-progress`) shows combined progress across every file in every selected item.
- Given a batch move is requested where any selected item cannot be validly moved (name conflict in the destination, a folder being moved into itself or its own descendant, or an attempt to move a category root), when the request is validated, then no item is moved and the user sees a clear error identifying that the batch could not proceed, exactly as today's single-item validation already behaves.
- Given a batch move job fails partway through the filesystem work, when the job stops, then already-moved items stay moved (no rollback, consistent with the existing single-item move job), the failure is reported with a count of how many of the total files were moved before the failure, and the listing is refreshed to reflect the true on-disk state.
- Given the user navigates to a different folder/category or triggers a rescan, when the listing reloads, then any existing multi-selection is cleared, since a selection only makes sense scoped to the folder it was made in.

## Functional Requirements

1. FR1 — Each card in `ArchiveBrowser.razor`'s grid (`WebApp/WebApp.Client/Components/ArchiveBrowser.razor:270-274`) gains a click handler that inspects `MouseEventArgs.CtrlKey`/`ShiftKey` (Blazor's built-in modifier flags — no new JS interop) before falling back to today's plain-click behavior (`ActivateAsync`). Ctrl+Click and Shift+Click never call `ActivateAsync`.
2. FR2 — Ctrl+Click (without Shift) toggles that single item's membership in a new `_selectedForMoveIds` (`HashSet<string>`) set and sets it as the new range anchor (`_selectionAnchorId`). Clicking an item that is already the sole selection with Ctrl+Click clears it.
3. FR3 — Shift+Click (with or without Ctrl held) computes the inclusive range between `_selectionAnchorId` and the clicked item's position in the current `_filteredItems` order (`WebApp/WebApp.Client/Components/ArchiveBrowser.razor:772`) and replaces `_selectedForMoveIds` with that contiguous range. If no anchor exists yet, Shift+Click behaves like Ctrl+Click (selects just that item and sets the anchor).
4. FR4 — Both files and folders can be part of a multi-select; a category root folder is never selectable this way (mirrors `EnsureNotCategoryRoot` server-side validation, `WebApp/WebApp/Services/ArchiveService.cs`).
5. FR5 — Each selected card shows a distinct visual state (a green card border) separate from and simultaneously compatible with the existing "currently playing" badge (`WebApp/WebApp.Client/Components/ArchiveBrowser.razor:279-284`); a card can show both states without visual conflict. (Decided during implementation: no separate per-card checkbox is rendered — the green border alone is sufficient, and Ctrl+Click/Shift+Click remain the only ways to build a selection.)
6. FR6 — When `_selectedForMoveIds.Count > 0`, a selection toolbar appears (Bootstrap `d-flex` bar using existing button/badge conventions) showing "`N` selected", a "Move" button, and a "Clear selection" (`bi-x-lg`) button. It does not block the rest of the browser (non-modal, matches the non-blocking assumption already adopted in `Specs/20260922122650-archive-move-delete-progress`). The "Move" button is disabled (not hidden) while an archive-mutation job is already in flight (`_activeJob is not null`) — only one move/delete progress popup is ever shown at a time, so the user must let the current job reach a terminal state (or dismiss its popup) before starting another move, whether single-item or batch.
7. FR7 — Selecting "Move" from the toolbar opens the existing `ArchiveMovePicker` component (`WebApp/WebApp.Client/Components/ArchiveMovePicker.razor`) with a batch-aware title (e.g. "Move 5 items") instead of a single item's name; `ArchiveMovePicker` gains an optional `TitleOverride` parameter for this, and its destination-browsing logic is otherwise unchanged.
8. FR8 — A new server endpoint `PATCH /api/archive/{category}/items/location` (no `{id}` segment, distinguishing it from the existing per-item route) accepts a `BatchMoveArchiveItemsRequest(IReadOnlyList<string> ItemIds, string DestinationCategory, string? DestinationFolderId)` body and is registered in `MapArchiveEndpoints` (`WebApp/WebApp/Endpoints/ArchiveEndpoints.cs:12-57`) alongside the existing `Move` route.
9. FR9 — A new `ArchiveService.BatchMove(string categoryKey, IReadOnlyList<string> itemIds, string destinationCategoryKey, string? destinationFolderId)` method validates every item synchronously up front — resolving each item, checking for a name conflict at the destination, and rejecting a folder moved into itself/its own descendant or a category root — exactly as `ArchiveService.Move` does per item today (`WebApp/WebApp/Services/ArchiveService.cs:180-204`). If any single item in the batch fails validation, the whole request is rejected (no partial enqueue) with the same exception types (`ArchiveValidationException`, `ArchiveConflictException`, `ArchiveForbiddenException`, `ArchiveNotFoundException`) the existing endpoint already maps to HTTP responses.
10. FR10 — `ArchiveMutationKind` (`WebApp/WebApp.Client/Models/ArchiveMutationKind.cs`) gains a `BatchMove` value. A validated batch produces one `ArchiveMutationJob` whose `TotalItems` is the sum of each selected item's own file count (folder file count, or 1 for a single file — same counting rule as today's single-item `Move`), carrying the list of per-item (source path, destination path, file count) entries needed to execute the whole batch as one job.
11. FR11 — `ArchiveMutationExecutor` (`WebApp/WebApp/Services/ArchiveMutationExecutor.cs`) gains a `BatchMoveAsync` method that processes the batch's entries one item at a time, reusing the existing single-file `File.Move`/recursive-folder-move logic per entry, and reports progress as a running total across all entries (not reset per entry) so the popup shows one combined "X of Y" count for the whole batch. If any entry fails partway through, the job stops (no further entries are processed) and reports how many of the total files across the whole batch were moved before the failure — consistent with the existing single-item "no rollback" behavior (`WebApp/WebApp/Services/ArchiveMutationExecutor.cs:78-82`).
12. FR12 — `ArchiveMutationBackgroundWorker` (`WebApp/WebApp/Services/ArchiveMutationBackgroundWorker.cs`) routes `ArchiveMutationKind.BatchMove` jobs to the new `BatchMoveAsync` executor method, following the same `switch` pattern already used for `Move`/`MoveToTrash`/`EmptyTrash`.
13. FR13 — The client's existing generic job-enqueue/poll flow (`EnqueueMutationAsync`, `_activeJob`, `StartJobPolling`/`PollJobAsync`, `WebApp/WebApp.Client/Components/ArchiveBrowser.razor:1700-1775`) is reused unchanged for the batch move job; only `JobActionLabel` (`WebApp/WebApp.Client/Components/ArchiveBrowser.razor:1783`) gains a `BatchMove` case (e.g. "Moving").
14. FR14 — On successful enqueue, on the listing reloading after a completed/failed job, and whenever `LoadAsync` loads a new folder/category (`WebApp/WebApp.Client/Components/ArchiveBrowser.razor:835`) or a filter/rescan clears the current item set, `_selectedForMoveIds` and `_selectionAnchorId` are cleared.
15. FR15 — All new endpoint payloads (job DTOs, batch request/response) expose only opaque item IDs, category keys, folder IDs, and counts — no physical or root-relative filesystem path, matching the existing opaque-ID boundary (`AGENTS.md` Constraints).

## Non-Functional Requirements

- No physical or root-relative filesystem path is ever exposed to the browser or written to normal application logs, consistent with the existing archive opaque-ID boundary.
- The batch-move responsibilities are split the same way the existing move/delete-progress pipeline already is: `ArchiveService` owns validation/path resolution, `ArchiveMutationExecutor` owns the actual file I/O, `ArchiveMutationBackgroundWorker`/`IArchiveMutationJobQueue`/`IArchiveMutationJobStatusStore` own scheduling and status — no new parallel pipeline is introduced.
- All new UI is built from Bootstrap components/utilities and Bootstrap Icons per `AGENTS.md`'s design-system constraints; the selection toolbar and green selected-card border reuse existing badge/button/border conventions already present in `ArchiveBrowser.razor` rather than introducing new bespoke styling.
- This feature is scoped to `ArchiveBrowser.razor`'s own category grid (Videos/Music/Documents/Images/custom folders/Trash), where per-item Move already exists. The unrelated checkbox-based selection in `VideoGrid.razor` (`SelectionEnabled`/`SelectedIds`/`OnToggleSelect`, used only by the Cuts section to build Video Compositions) is not modified, reused, or renamed by this spec — it is a separate feature over a separate item type (`VideoItemDto`, not `ArchiveItemDto`) with no destination-folder concept.
- Existing single-item move behavior (`StartMoveFromActions`/`StartMove`/`MoveAsync`, the single-item `PATCH .../items/{id}/location` route) is unchanged; this spec adds a batch path alongside it rather than replacing it.

## Out of Scope

- Multi-select for "Move to Trash"/delete, rename, or any other bulk action — only bulk Move is in scope, per explicit product decision.
- Adding Ctrl+Click/Shift+Click multi-select to `VideoGrid.razor` (Video Library, Cuts, Video Compositions) — those grids show `VideoItemDto` items with no destination-folder/Move concept today, and `VideoGrid`'s existing composition checkbox selection is explicitly out of scope to touch.
- Drag-and-drop of selected items onto a folder card (desktop-file-manager drag semantics) — selection here only feeds the existing modal move picker.
- Cross-category multi-select persistence (e.g., keeping a selection while navigating between categories) — a selection is scoped to the current folder listing and is cleared on navigation.
- Automatic rollback of a partially-completed batch move on failure (matches the existing single-item "no rollback" precedent).
- Keyboard-only range selection (e.g., Shift+Arrow keys) and any touch/checkbox-based equivalent to Ctrl+Click — only mouse/pointer Ctrl+Click and Shift+Click are in scope.

## Open Questions

Both prior open questions are resolved:

- Shift+Click alone (Ctrl not required) extends the range from the anchor — standard Dolphin/OS file-manager behavior. Ctrl+Shift+Click also works identically (Ctrl is simply ignored when Shift is held).
- The selection toolbar's "Move" action is disabled (not hidden) while another archive-mutation job is already in flight (`_activeJob is not null`); the user must wait for the in-progress job's popup to reach a terminal state (or dismiss it) before starting another move, matching the existing one-job-at-a-time queue and keeping only one progress popup visible at a time.
